# Security Policy & Security Standards

PRAJNA is designed to process and protect sensitive faculty profiles, achievements, compliance records, and academic data. This document describes our security standards, tools, and vulnerability reporting procedures.

---

## 🛡️ 1. Security Tools Configuration (Free GitHub Capabilities)

We configure and run these scanning tools to maintain high security standards on GitHub's free plan:

### Dependency Graph & Dependabot
- **Dependency Graph:** Enabled under Repository Settings to index external libraries.
- **Dependabot Alerts:** Scans npm modules for vulnerabilities. Developers will receive alerts if dependencies have known issues.
- **Dependabot Security Updates:** Automatically opens Pull Requests to update vulnerable npm packages to patch versions.

### Secret Scanning & Push Protection
- **Secret Scanning:** Scans commits for exposed API keys, AWS credentials, and DB connections.
- **Push Protection:** Block commits that contain suspected secrets *before* they are pushed to GitHub. This is enabled on the repository configuration page.

## ☁️ 2. AWS CDK & Infrastructure Security Standards

Because we use TypeScript AWS CDK for infrastructure deployment, we enforce several static-analysis tools:

### cdk-nag Rulesets
All CDK stacks must run `cdk-nag` during tests and synthesize cycles. We use the `AwsSolutionsChecks` ruleset.
- **Rules checked:** Unencrypted S3 buckets, open security groups, lack of API Gateway throttling, and public read/write configurations.
- **Enforcement:** Stacks must pass validation in the CI pipeline. High-severity violations will fail the build.

### Checkov Integration
Checkov scans compiled CloudFormation templates generated by `cdk synth` for common misconfigurations.
- **Rules checked:** Missing server-side encryption, IAM policy actions containing wildcards (`*`), and lack of encryption-at-rest on DynamoDB tables.
- **Enforcement:** Checkov is executed during the linting phase of the Pull Request workflow.

### Least-Privilege IAM Roles
- **No Shared Roles:** Every Lambda function must have its own dedicated IAM role.
- **Resource Constraints:** Avoid `Resource: "*"` in IAM statements. Restrict actions (e.g. `dynamodb:PutItem`, `s3:GetObject`) specifically to the resource ARN.
- **Action Constraints:** Do not use admin actions like `s3:*` or `dynamodb:*`. List specific operations needed.

## 📬 3. Reporting a Vulnerability

If you discover a security vulnerability, please do **NOT** open a public issue on GitHub. Instead, report it through the private channel:

1. Send an email to the Security Coordinator: **security-prajna@gitam.edu** (mock) or contact the Lead Architect: **@Navaneeth Kumar Buddi**.
2. Include a detailed description of the vulnerability, steps to reproduce, and a proof of concept if possible.
3. The team will acknowledge receipt of the report within **48 hours** and coordinate a patch.
4. Once resolved, the vulnerability will be disclosed, and contributors will be credited in the release notes.
